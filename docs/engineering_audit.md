# Engineering audit — 2026-09-24

## Scope and baseline

RiverLab is a browser-local 2–6 seat no-limit Texas Hold'em trainer. The pure TypeScript engine owns hand state, action validation, pots, evaluation and settlement; React orchestrates human/AI turns; versioned LocalStorage stores settings and completed hands. There is no multiplayer server or database transaction layer. The Cloudflare Worker serves the app and assets.

At intake, `main` tracked `origin/main` at `0448372`. Four pre-existing untracked historical copies under `.codex/` and `docs/` were preserved. The existing Chromium suite passed 13/13. The initial repository `npm run check` was interrupted during ESLint because local cloud-backed `node_modules` reads stalled; a direct Vitest attempt reached no tests because fork startup timed out. No test assertion failed in those interrupted runs. A clean isolated install of the current source and lockfile supplied the full quality baseline before the dependency update: formatting, lint, types, 123 tests and build all passed. The previously documented test count was 112; this audit added 11 tests.

## Coverage and validation

Added deterministic regression tests for malformed actions, card/stack/identity validation, short-stack scenario rejection, three side pots, an odd-chip main-pot tie with a distinct side-pot winner, malformed saved data, and Monte Carlo count boundaries. Existing tests cover all nine standard hand categories, wheel/kickers, heads-up order, short raises, all-ins, chip conservation, card uniqueness and 120 seeded six-player hands.

The clean candidate passed `npm run check`: Prettier, ESLint, strict TypeScript, 13 Vitest files / 123 tests, and vinext production build. The final patched candidate passed 13/13 Chromium and 7/7 WebKit flows. `npm run start` served the built app with HTTP 200 and the expected RiverLab title. The official npm registry production audit moved from 5 package findings (1 critical, 3 high, 1 moderate) to 0 after the dependency update. The complete audit moved from 14 package findings to 7 high findings. `git diff --check` and repository `npm run format:check` also passed.

Validation used a clean temporary copy of this source and the exact committed lockfile because this Mac's pre-existing, ignored `node_modules` was being hydrated from cloud storage and timed out launching Vitest workers. The repository's existing `node_modules` was left intact to preserve local state; run `npm ci` in this checkout when updating its installed dependencies.

The Next.js security findings were the official [Windows server advisory](https://github.com/advisories/GHSA-p293-qw3h-jr36) and [AVIF image optimization advisory](https://github.com/advisories/GHSA-2xp9-vwfh-vxw4). The dependency update used the [stable Next.js release](https://github.com/vercel/next.js/releases/tag/v16.3.6).

## Remaining limits

- Because the full game runs in one browser, its client memory contains the deck and other players' cards. They are hidden in the UI and absent from AI observations, but a user can inspect their own local runtime. Preventing that would require a trusted server and a different product architecture.
- LocalStorage has no cross-device synchronization or multi-tab conflict resolution; the last tab to write wins. Storage quota failures currently return `false` from `saveData` without a persistent user-facing recovery flow.
- Desktop Playwright WebKit cannot establish physical iPhone/iPad safe-area and touch behavior. A real-device pass remains useful before a mobile release.
- Dependency audit results are time-sensitive. Recheck the official registry during future releases.
- The seven remaining complete-audit findings are confined to the Cloudflare/vinext development and preview toolchain (`@cloudflare/vite-plugin`, Miniflare, Wrangler, undici, Sharp, vinext and image-size). The current plugin fix requires Miniflare 5 alpha; the vinext fix requires a beta major upgrade. Those compatibility changes were not applied without targeted runtime/deployment testing.

## Independent release-candidate review — 2026-09-24

This second pass challenged the working candidate, including the previous uncommitted diff. It did not rely on the earlier verdict. The original 123 tests passed again before the new adversarial cases. No commits, pushes, dependency upgrades, or deletion of pre-existing working changes were performed during this review.

The heads-up adjustment and short-raise interpretation were checked against [TDA rules 36-C and 49](https://www.pokertda.com/view-poker-tda-rules/). A suspected short-opening-all-in minimum-raise defect was **not** confirmed: the existing no-limit rule correctly adds the full minimum increment, and a previous checker cannot raise unless facing a full bet. No rule change was made there.

Retained product limits: a browser-local trainer exposes its state to its owner through developer tools; no multiplayer security boundary or server persistence exists. Forced-blind scenarios that already settle at initialization remain explicitly rejected.
